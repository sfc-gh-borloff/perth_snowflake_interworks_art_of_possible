What you will build

An Intelligent Sales Assistant for Summit Gear Co., a fictional outdoor adventure brand. In one hour, driving CoCo Desktop conversationally, you will have:

A loaded dataset

200 deals and 150 sales-call transcripts, generated by describing what you want — no CSVs, no manual DDL.

A Cortex Search service

Hybrid semantic and keyword search over unstructured call transcripts.

A Semantic View

Business context that lets Cortex Analyst turn plain English into accurate SQL.

A deployed Cortex Agent

One agent that orchestrates across both structured and unstructured data.

The same agent in CoWork

Your agent used by a business person in a chat interface — no code, no extra deployment.

Everything here is sample data. Nothing in this lab touches your own systems, and you do not need to bring any data. Summit Gear Co. is invented, and CoCo generates the whole dataset for you in Module 1. That means you can be completely unguarded about what you try — break things, ask awkward questions, drop the database and start again.

This runs entirely in CoCo Desktop

CoCo comes in two forms — a desktop application and a command-line tool — and they are the same agent underneath, driving the same Snowflake account. Today we are using CoCo Desktop throughout. Every prompt in this guide is typed into the Desktop chat panel.

If you would rather use the CLI, you can. The published quickstart this lab follows is written for the CLI, and every build step in it is a conversational prompt — so the prompts below are identical in either. If you already live in a terminal, go ahead. But Desktop is what we will be demonstrating from the front, and it is the easier place to see what CoCo is actually doing: the chat, your files, the SQL it ran and the objects it created are all in one window.

Work however suits you

You are welcome to work on your own or alongside the people from your organisation. Plenty of people get more out of it in pairs, swapping at each module boundary:

Driver

Hands on keyboard. Runs CoCo, pastes prompts, reads what comes back out loud.

Navigator

Reads ahead in this guide, watches what CoCo is actually doing, and asks "why did it choose that?" Catches what the driver misses.

If you are in a business, analyst or leadership role, consider taking Navigator first. You do not need to type a command to get the value here, and this lab is not a coding test. The navigator seat is actually the better one for understanding what just happened: what CoCo decided on its own, what it asked your permission for, and how little of this was hand-written SQL. Then take the keyboard at Module 4, where the agent gets built — that is the part worth having done yourself.

You should have done this before arriving. If CoCo Desktop is already open and connected, help your neighbour and read ahead to Module 1.

Open CoCo Desktop. On first launch it walks you through connecting to your Snowflake trial account. Once you are at the chat panel, confirm you are pointed at the right place and have the privileges you need — type this into the chat:

What Snowflake account, user and role am I currently connected as?
Confirm I can create databases, warehouses, Cortex Search services,
semantic views and agents with this role.
  • CoCo Desktop opens and the chat panel responds
  • It reports your trial account identifier and your user

1 · Generate the dataset 12 min

You will not write a CREATE TABLE statement or load a file. You will describe the dataset you want, and CoCo will design it, build it and populate it.

Paste this into the CoCo Desktop chat exactly as written:

Set up a sales database for Summit Gear Co., an outdoor adventure brand.
Create database SUMMIT_GEAR_CO with schema SALES and a small warehouse called SUMMIT_GEAR_WH.
Then generate and load synthetic data into two tables:

Table 1: DEALS (200 rows)
Columns: deal_id, customer_name, deal_value, close_date, sales_stage, win_status, sales_rep, territory, product_name, product_category
- 8 sales reps: Jake Morrison, Mia Chen, Lucas Rivera, Ava Patel, Ethan Brooks, Sophie Nakamura, Caleb Washington, Lily O'Brien
- 4 territories: Pacific Northwest, Mountain West, Northeast, Southeast
- 30 customers (outdoor retailers and e-commerce): REI, Backcountry, Moosejaw, Mountain Hardwear Outlet, Wild Earth, Campmor, Sierra Trading, Steep & Cheap, Eastern Mountain Sports, Outdoor Voices, Fjallraven Store, Sundance Outfitters, Trailhead Sports, Alpine Start, Summit Supply, Peak Performance Shop, Ridge & River Co, Basecamp Goods, Powder House, Timberline Traders, The North Wall, Canyon Creek Outfitters, Glacier Point Gear, High Camp Provisions, Ridgeline Sports, Evergreen Adventures, Crestline Outdoors, BlueSky Gear, TerraPeak Supply, Venture Out Co
- 12 products across 4 categories: Boots (Alpine Pro, Trail Runner, Winter Grip), Jackets (Summit Shell, Basecamp Down, Storm Guard), Packs (Expedition 65L, Day Hiker 30L, Ultra Light 20L), Accessories (Trekking Poles, Headlamp Pro, Thermal Flask)
- Sales stages: Closed Won, Lost, Pending, Negotiation, Discovery
- Deal values ranging from $5,000 to $150,000
- Close dates to our current date

Table 2: SALES_CONVERSATIONS (150 rows)
Columns: conversation_id, transcript_text, customer_name, deal_stage, sales_rep, territory, conversation_date, deal_value, product_name
- transcript_text should be realistic 3-5 paragraph sales call transcripts discussing products, customer objections, competition, seasonal demand, pricing negotiations, and inventory concerns
- Reference actual product names and customer names from the lists above
- Include variety: discovery calls, demos, negotiations, closing conversations, and follow-ups

After loading, enable change tracking on SALES_CONVERSATIONS.

This is the longest wait in the lab — 150 three-to-five paragraph transcripts is a lot of text to generate. Use the time: read ahead to Module 2, and watch what CoCo is doing in the meantime. It is choosing the DDL, picking data types, and stopping to ask your approval before it changes anything. That approval step is worth noticing: it is not running unattended.

Verify before you move on

How many rows are in SUMMIT_GEAR_CO.SALES.DEALS and SUMMIT_GEAR_CO.SALES.SALES_CONVERSATIONS?
  • DEALS returns 200 rows
  • SALES_CONVERSATIONS returns 150 rows
  • Spot-check that one transcript is real prose, not placeholder text: Show me one full transcript_text from SALES_CONVERSATIONS
Short on rows? That is normal and not a failure — generation sometimes stops early. Say Top up SALES_CONVERSATIONS to 150 rows with the same generation rules. Anything above about 40 transcripts is enough to continue; do not spend more than two minutes here.

2 · Create the Cortex Search service 6 min

Those transcripts are unstructured text — the kind of data that normally never makes it into a dashboard. Cortex Search gives you hybrid semantic and keyword retrieval over them, with managed embeddings. You do not pick a model, build a pipeline, or manage a vector store.

Create a Cortex Search service called SALES_CALL_SEARCH on the transcript_text column
in SUMMIT_GEAR_CO.SALES.SALES_CONVERSATIONS with attributes customer_name, deal_stage,
sales_rep, territory, product_name using warehouse SUMMIT_GEAR_WH

CoCo looks up the correct syntax and executes it. The service then builds a semantic index across your transcripts.

Why the attributes matter

Those five attribute columns are what let the agent filter while it searches. A question like "objections in the Northeast about Alpine Pro boots" needs both semantic matching on the text and a filter on territory and product. Ask CoCo to explain it in its own words:

Explain what the attribute columns do in a Cortex Search service
and why I would not just put everything in the search column.
  • Service SALES_CALL_SEARCH created
  • Indexing has started (ask What is the status of the SALES_CALL_SEARCH service?)

3 · Create the Semantic View 8 min

This is the step that drives text-to-SQL accuracy, and it is the one most worth understanding. A Semantic View adds business meaning — descriptions, synonyms, sample values, relationships — on top of raw columns, so that "win rate" or "how are we tracking" means something specific and agreed, rather than something the model guesses at.

Create a semantic view for the SUMMIT_GEAR_CO.SALES.DEALS table

CoCo loads its built-in semantic-view skill, which generates the view from table metadata, annotates columns with descriptions, sample values and synonyms, then deploys it. Accept the defaults when prompted for naming and file location.

Open what it generated and read it before you accept. This is the difference between an assistant that answers 60% of questions and one that answers 90%. In your own organisation, this file is where your domain knowledge lives — what your business actually calls things, which definition of "active customer" is the real one. And because it is a file, it is reviewable, diffable and version-controlled, which is the answer to the first question your governance people will ask.

Now improve it, which is exactly what you would do on your own data:

Add a metric to the semantic view for win rate, defined as the count of deals
where win_status indicates a win, divided by the count of all closed deals.
Add synonyms for territory including region and area.
  • Semantic view deployed over DEALS
  • You have read the generated descriptions and synonyms
  • A win-rate metric exists

4 · Build the Agent 10 min

Swap seats now if you have not already. This is the module everyone should drive.

Right now you have two separate capabilities: search over text, and analytics over structured data. A Cortex Agent puts one orchestration layer in front of both, so that a person asks a question in plain English and the agent decides which tool to use — or both.

Create an agent called SUMMIT_GEAR_AGENT in SUMMIT_GEAR_CO.SALES that uses the
SALES_CALL_SEARCH cortex search service and the deals semantic view

CoCo loads its cortex-agent skill and will:

  1. Initialise an agent workspace
  2. Build the agent specification with both tools attached
  3. Generate orchestration instructions that route questions to the right tool
  4. Deploy the agent
Read the orchestration instructions before you deploy. This is the most important thing in the agent spec and the thing most people skip past. It is natural-language routing logic — it tells the agent when to search transcripts and when to query deals. When someone asks you "but how do we control what the AI does?", this file is the answer. Ask CoCo: Show me the orchestration instructions you generated and explain the routing logic.
  • Agent SUMMIT_GEAR_AGENT deployed in SUMMIT_GEAR_CO.SALES
  • It has two tools: a Cortex Search tool and a Cortex Analyst tool
  • You have read the orchestration instructions

5 · Test the Agent 8 min

Three questions, each proving something different. Run all three — the third is the one that matters.

Structured — routes to Cortex Analyst

Chat with agent SUMMIT_GEAR_CO.SALES.SUMMIT_GEAR_AGENT and ask:
What is our win rate by territory this quarter?

This generates SQL against DEALS and aggregates by territory. A dashboard could have told you this.

Unstructured — routes to Cortex Search

Ask the agent: What objections came up in recent calls about our Alpine Pro boots?

This retrieves relevant transcripts and surfaces customer objections, with citations back to the specific calls. A dashboard could not have told you this.

Both — the orchestration test

Ask the agent: How is Sophie Nakamura performing in the Northeast,
and what themes come up in her sales calls?

This requires the agent to pull deal metrics and search her transcripts, then reconcile them into a single answer. This is the one to pay attention to. It is the capability that does not exist in a BI tool or a general-purpose chatbot, and it is the thing worth going back and telling your colleagues about.

Now try to break it. Ask something your data genuinely cannot answer — What is our market share in Japan? — and watch whether the agent abstains rather than inventing a number. Answer abstention is a feature, not a limitation, and being able to demonstrate it is often what gets an AI project approved rather than shelved.
  • All three questions answered sensibly
  • Citations appear on the transcript-based answer
  • You have seen the agent decline to answer something unanswerable

6 · Hand it over: your agent in CoWork 8 min

You have built an agent as a builder. Now see it the way the rest of your organisation will. This is the point of the whole architecture: CoCo is where you build, CoWork is where the business consumes. It is the same agent object in both — you will not deploy anything again.

  1. Open Snowsight in your browser, signed in to the same trial account.
  2. Open Snowflake CoWork.
  3. Select your agent, SUMMIT_GEAR_AGENT.
  4. Ask it the way a sales manager would, not the way a builder would: "Which territory is underperforming and why?"

Notice what is different, and notice what is identical. Same agent, same tools, same semantic view, same governance and role-based access control. No code, no terminal, no deployment step, no copy of the data. You did nothing extra to make it available here.

This is the slide you cannot put on a slide. If you take one thing back to your organisation from this morning, make it this: the person who builds the agent and the person who uses it are working with the same governed object, and the handover between them costs nothing. The gap between "the data team prototyped something" and "the business is using it" is usually where these projects die.
If your agent does not appear in CoWork, do not debug it now. Flag it to a facilitator and carry on — you can complete the rest of the morning entirely from CoCo Desktop. Availability can vary by trial account and region, and one of us will come and look at it with you.
  • Agent located in CoWork
  • A business-phrased question answered without touching a terminal

7 · Teach CoCo your standards with AGENTS.md Optional — 5 min

Only do this module if you are ahead of the room. It is genuinely useful, but it is an engineering-practice module rather than a capability one, and nothing later depends on it. If you are at this point with time to spare, carry on. Otherwise skip it — pick it up in the extended session after the break, or at home. The guide is yours to keep.

Everything so far, you told CoCo explicitly. That does not scale. In a real project you have naming conventions, a warehouse you are allowed to use, and things you must never do. AGENTS.md is how you write that down once.

What AGENTS.md is

A plain Markdown file in your project folder that CoCo reads automatically at the start of every session. No command, no install, no configuration. It is persistent project context: conventions, commands, guardrails and preferences. Think of it as onboarding documentation that your assistant actually reads — and it is exactly the kind of file Desktop is built to work with, since you can see it, the chat, and the changes CoCo proposes all at once.

Create or open a project folder in Desktop, then ask CoCo to write it:

Create an AGENTS.md in this project that captures the following, and keep it concise:

## Snowflake
- Database SUMMIT_GEAR_CO, schema SALES, warehouse SUMMIT_GEAR_WH. Never use another warehouse.
- Never run DROP or TRUNCATE without asking me first.
- Always qualify objects to three parts.

## Naming Conventions
- Tables and columns UPPER_SNAKE_CASE. Semantic views suffixed _SV. Agents suffixed _AGENT.
- Cortex Search services suffixed _SEARCH.

## Semantic Views
- Every column gets a description. Every dimension a business user would name differently gets synonyms.
- Define metrics explicitly rather than relying on the model to infer aggregations.

## How I want you to work
- Show me the SQL or spec before you deploy anything.
- Explain your reasoning in one or two sentences, not an essay.

Prove it works

This is the whole point of the module — do not skip the test. Ask for something that would break a rule, without restating the rule:

Create a semantic view over the SALES_CONVERSATIONS table.

Watch what CoCo does differently: it should apply your _SV suffix, stay on SUMMIT_GEAR_WH, write descriptions on every column, and show you the spec before deploying. You asked for none of that in that prompt.

  • AGENTS.md exists in your project folder
  • A follow-up request visibly obeyed a rule you did not repeat
